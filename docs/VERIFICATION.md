# 自检报告：方法、范围、结论与可信度

- 对象：`dsh-quick-adb@0.2.0`（TypeScript 无关，纯 ESM；lib 约 3.1k 行 / scripts 约 0.7k 行）
- 时间：2026-11-01
- 结论摘要：**45 项已知问题全部关闭**（43 修复 / 2 按设计保留）；自测 94 项（含 dsh 环境 115 项）全绿。性能结论已按第三方真机复测修正：**只在需要感知的流程里成立，固定坐标流水线是负优化**。
- 本文件回答四件事：**怎么查的、查了什么、逐项结论、这个结论有多可信**。

## 2. 方法

不是「读一遍凭感觉」，而是五类手段交叉：

| 手段 | 具体做法 | 产出 |
|---|---|---|
| **A. 静态通读** | 逐文件读，重点看「状态在哪儿被改」「异常往哪儿抛」 | 26 项静态可疑点 |
| **B. 跨文件契约核对** | 同一语义在多处实现是否一致（如「动作后必须失效缓存」在 tap/swipe/input/key/batch 五处） | 发现 batch 漏失效（P1-1）与四份重复实现（P3-2） |
| **C. 动态取证** | 写一次性探针脚本，用替身设备把可疑点跑成输出（不是"应该会"而是"确实会"） | 确认 4 个缺陷：注入、开关绕过、旧树复用、nth 钳制 |
| **D. 故障注入** | 给 `mock-device` 加 `faults`（压缩不支持/空层级/超时/坏 PNG/探测不符），强制走错误分支 | 补齐原先零覆盖的 9 条错误路径 |
| **E. 对照实测** | 在同一台替身设备上跑「朴素三步式」，实测往返数作为基线 | 基线从"假设 3"变成"实测 3.00" |
| **F. 外部复测比对** | 第三方在真机+真实网络链路复测（RTT 125ms），逐项比对本仓库结论 | 推翻 2 条过度概括，暴露 6 个 mock 测不出的问题（R1–R6） |

判定口径：**只有 C/D 能复现的才记为缺陷**；仅静态可疑但无法构造触发的，记为「待观察」并不计入修复表（本次为 0 项）。

## 3. 逐项检查结论

### 3.1 逻辑正确性

| 检查项 | 方法 | 结论 |
|---|---|---|
| 缓存失效时机（动作后是否一定重解析） | B+C | **缺陷 P1-1**（batch 漏失效）→ 已修 |
| 分层判定 L1/L2/L3 是否互斥且覆盖 | A+C | 正确；L2 在探测失配时回落 L3 |
| 选择器评分与提升是否可能选错 | A+C | 正确；但 `nth` 越界静默取末尾 → **P1-2** → 已修 |
| 批处理「先解析后下发」的顺序一致性 | A | 正确；切段后仍按序执行 |
| 动作结果与缓存状态是否一致 | B | 四处实现重复导致语义漂移 → **P3-2** → 已统一 |
| 设备未解析时能否发命令 | A | **新发现**：batch 未 `device()` → 已修 |
| 配置项是否都被消费 | B | `includeScreenInAction`、`logLevel` 是死配置 → 已接 |
| 面板/工具渲染是否漏字段 | B | `find` 未渲染 → **P1-3** → 已修 |

### 3.2 边界与异常

| 检查项 | 方法 | 结论 |
|---|---|---|
| `nth` 越界 | C | 静默钳制 → 已改为报错 |
| 坐标为字符串 | C | 误报"缺参数" → 已修（先 Number） |
| `maxTexts = 0` | A+C | off-by-one → 已修 |
| `input text` 含 `%` / 非 ASCII | A+C | 文本可能被改写 → 已改为告警/走 base64 |
| `wait` 超时上界 | C | 700ms 实测 1562ms → 已修（307ms） |
| dump 返回空层级 / 超时 / 不支持压缩 | D | 降级链正确；但一次超时会永久关压缩 → **P2-3** → 已修 |
| 截图不是合法 PNG | D | 有 pull 兜底；坏图路径已测 |
| 批处理累计时长撞超时 | A | 无保护 → **P2-11** → 已按预算切段 |

### 3.3 错误处理

| 检查项 | 结论 |
|---|---|
| 错误是否都转成「模型可读 + 可操作」 | 是。未命中给候选文案与匹配数；dump 失败给尝试明细；超时给最后界面摘要 |
| 是否吞异常导致静默失败 | 修复前有 2 处（batch 无效失效、`slice(-1)`）→ 已修 |
| 失败后设备状态是否可解释 | batch 返回 `steps` 序列 + `failedStep` + `cacheInvalidated` |
| 错误类型是否被上层消费 | `ActionError.kind` 目前仅用于文案分支，未做统一降级策略（可接受） |

### 3.4 性能

| 检查项 | 结论 |
|---|---|
| 往返次数 | 实测 0.38 次/步（朴素 3.00）；单步动作 1 次 |

| 超时重试放大 | dump 最多 2 次；`wait` 有预算保护；batch 有切段 |

| 资源增长 | 截图原无上限 → 已加 `maxShots` |

### 3.5 安全

| 检查项 | 结论 |

## 4. 整体可信度评估

| 结论类别 | 可信度 | 理由 |
|---|---|---|
| 「这些缺陷确实存在」 | **高** | 4 个关键项有脚本化取证输出，可复跑 |
| 「这些缺陷已被修复」 | **高** | 每项都有对应断言，改坏即红（本次修复过程中就红过 3 次） |
| 「往返次数与耗时的改善幅度」 | **中** | mock 延迟是常量；真机复测证实「需要感知的流程」有效，但固定坐标流水线为 -32% |
| 「缓存分层在真机上是否安全」 | **中高** | 逻辑与测试完备，但同 Activity 弹窗、闪烁界面未真机验证 |
| 「在真实 dsh 进程内可正常装载」 | **中** | 按生产插件（onebot）的契约比对 + shim 冒烟，未跑真实宿主 |
| 「跨 ROM / Android 版本兼容」 | **低** | 无真机，`uiautomator` 各厂商差异未覆盖 |

**总评**：作为「代码级缺陷与测试有效性」的结论，可信度**高**；作为「真机性能与兼容性」的结论，可信度**中偏低**。两者不要混用。

## 5. 可信度的判断依据

1. **可复现**：所有缺陷证据来自脚本（selftest 的 64 条断言 + bench），不是人工观察；任何人 `node scripts/selftest.mjs` 都能得到同一结果。
2. **双路径**：每个结论都同时经过「读码定位」与「运行验证」；只有单路径的记为待观察，不计入修复表。
3. **失败可注入**：错误分支不是"看着对"，而是用 `faults` 强制触发（压缩不支持、空层级、超时、坏 PNG、探测失配）。
4. **对照实测**：优化幅度不是拿假设基线对比，而是在同一台替身设备上实跑朴素链路得到 3.00 次/步。
5. **回归锁定**：每个 P0/P1 都映射到具体断言（AUDIT 表最后一列），修复不可悄悄回退。

## 6. 局限（请连同结论一起读）

1. **本仓库无真机**：验证跑在替身设备上；已有第三方真机复测补齐了「真实链路」这一环，但仍是单一机型（荣耀平板 Android 16），跨 ROM 差异未覆盖。
2. **mock 保真度有限**：延迟是常量，不模拟 RTT 抖动、CPU 抢占、设备卡顿；因此"5.1×"是**结构性估算**，不是真机实测值。
3. **模型侧延迟不可测**：识图 2500ms、生成代码 1200ms 是外部常量（bench 参数），本仓库无法测量，只能由使用者用自己日志填入。
4. **dsh 未真实装载**：工具契约依据生产插件 onebot 的用法与 `dsh-plugin-manager` 文档比对；shim 只能验证注册/渲染，不覆盖版本差异与宿主调度。
5. **并发未压测**：插件内部是串行队列，工具标记 `isConcurrencySafe:false`；高并发下的排队与超时行为未测。
6. **无 CI**：回归靠手动执行，没有流水线强制。
7. **审计者偏差**：同一个人写代码又审代码，盲区可能重叠；缓解手段是引入外部证据（运行输出）而非只靠判断。
8. **覆盖非穷尽**：超大界面（>2000 节点）、畸形 XML、超长文本、分屏/画中画未做压力测试。
9. **曾发布过未加限定的性能数字**：README 早期用 mock 数据写「单步 0.8s / 5×」，被真机复测证伪（真实 dump 2.4s，单步 3s 量级）。已修正，但说明「用 mock 反推用户体验」本身就是方法缺陷。

## 7. 如何自行复核

```bash
node scripts/selftest.mjs                               # 94 项断言
DSH_ADB_SELFTEST_VERBOSE=1 node scripts/selftest.mjs     # 附计时报告
node scripts/bench.mjs --steps 5                        # 结构性 A/B
node scripts/bench.mjs --real --serial <ip:5555> \
  --vision-ms <你的识图耗时> --gen-ms <你的生成耗时>      # 真机 A/B
```

真机复核建议顺序：先跑 `adb_screen` 确认控件树可用 → 再跑 `adb_batch` 三步流程确认 1 次往返 → 最后用 `--real` 做 10 步 A/B，把 `baselineStepMs` 写回配置。
