# 为什么这套方案能达成目标

这份文档不复述功能，只回答一个问题：**凭什么认为"单步从秒级降到亚秒级"不是运气，而是结构性的？**

---

## 1. 先把目标翻译成可测的量

原始目标是一句话：「每一步都要截图识图再生成代码，单步太慢，把它加快」。
可测形式只有一个：**单步墙钟时间 T_step**，以及它的构成。

把旧流程拆开，一步的真实成本是四项之和：

```
T_step = T_perceive + T_decide + T_act + T_glue

T_perceive  截图上传 + 视觉模型推理         ≈ 1.5–4 s
T_decide    模型重新生成一段可执行代码        ≈ 0.5–2 s（还带不确定性）
T_act       一次 ADB 动作                   ≈ 30–80 ms
T_glue      为了"看清结果"再补的 dump/cat/sleep ≈ 0.6–1.2 s
```

四项里，`T_act` 只占 2–5%。**慢的不是手机，是"让模型参与每一步"。**
所以真正的目标是：**把模型从执行回路里挪出去，只保留在决策回路里**。

---

## 2. 四个杠杆，以及它们为什么成立

### 杠杆一：换通道——从位图到结构

同一块屏幕：

| | 截图 | `uiautomator dump` |
|---|---|---|
| 数据形态 | 1080×2400×4B ≈ 10 MB 原始位图 | 20–80 KB XML |
| 语义 | 像素，坐标要"猜" | 文本 / id / 类名 / 可点击性 / 精确 bounds |
| 处理者 | 必须多模态模型 | 本地正则解析，毫秒级 |
| 可复现 | 每次可能不同 | 同一界面完全一致 |

这不是"更快地看图"，而是**换了一条信息通道**：识别问题从「模型估计」变成「字符串匹配」，后者是确定性算法，不需要推理，也就不需要等推理。

> 成立条件：界面是原生控件。自绘界面（WebView/Flutter/游戏）这条通道没有信息，杠杆失效——所以插件保留视觉兜底，而不是宣称通杀。

### 杠杆二：收敛动作空间——把"生成代码"降级为"填参数"

旧流程每步都要模型写一段 adb 脚本。这有两个成本：生成耗时，以及**生成结果不可预期**（同一意图两种写法，一种点得中一种点不中）。

插件把动作空间固定成 10 个工具 + 一个选择器对象。模型只需输出 `{"text":"搜索"}`，坐标由插件在控件树上算。

- token 从"一段代码"降到"一个 JSON"；
- 定位从"模型猜坐标"变成"评分 + 可点击性提升"，可解释、可回归；
- 失败有确定语义（未命中 / nth 越界 / 控件树不可用），而不是一段跑不通的代码。

> 这一步把 `T_decide` 从"生成 + 调试"降到"填参"，同时降低了方差。

### 杠杆三：合并往返——把线性项变成常数项

朴素实现一步要 3 次往返（dump / cat / input），而且每次往返之间还要本地 sleep 等界面稳定。
插件把「动作 + 等待 + 重新解析」拼成**一条** shell：

```
input tap X Y; sleep 0.25; uiautomator dump ...; cat ...
```

ADB 的 RTT 在这个部署形态下是 20–80 ms（USB 更低、网络 adb 更高），三次往返 ≈ 3×RTT + 2 次调度开销；合并后 = 1×RTT。**这是纯线性收益，与界面复杂度无关**，所以最稳。

更重要的是：这条脚本**顺带把新界面带回来了**，于是"下一步的感知"也被这次往返付掉了。实际观测到的效果是 3 步批处理只需 1 次往返（`selftest §7`），综合 8 步场景 0.38 次/步（`selftest` 汇总表，对照实测朴素链路 3.00 次/步）。

### 杠杆四：复用——同一界面内的读取从 O(n) 变 O(1)

模型的真实行为是"看一次界面，连着做几个判断"。旧流程每次判断都要重新截图。
插件缓存最近一次解析结果，并分级判定它还可不可信：

```
L1  无动作 + ≤800ms            → 0 次往返
L2  无动作 + ≤15s + 焦点探测一致 → 1 次 ~110ms
L3  做过动作 / 过期 / 探测不符   → 1 次往返（重新解析）
```

关键在于**"做过动作"一定降级到 L3**：宁可多花一次往返，也不拿旧树去点新界面。这让"复用"不牺牲正确性。

> 实测：同屏连续 3 次感知 = 1 次往返（`selftest §3`）；L2 命中 = 1 次 110ms（`§4`）。

## 3. 定量：新模型长什么样

```
T_new = dump_first + N × (RTT + settle) + H × 0 + M × (dump_time)
         首次       每个动作        命中    未命中
```

代入实测参数（RTT≈40ms、settle=250ms、dump≈520ms、命中率 70%）：

- 单步动作：≈ 810 ms（`bench` 实测 833 ms）
- 旧流程（识图 2500 + 生成 1200 + 截图 480 + 动作 45）：≈ 4241 ms
- 比值 ≈ **5.1×**

注意这个加速比**不依赖模型变快**。即使识图从 2500ms 降到 500ms，旧流程仍是 ~1700ms，插件仍是 4× 左右。真正被消除的是"每步都要模型在环"这件事本身。

## 4. 为什么这不是"偷工减料"

快而错没有意义。正确性由四条硬约束保证：

1. **定位是确定性的**：同一棵树上，同一选择器的结果可复现（评分规则固定），可以写回归测试。
2. **动作后必失效**：所有写操作走同一个 `runAction()` 出口，`settle:none` 或重建失败都强制 `dirty`（审计 P1-1 就是漏了这条，已修）。
3. **兜底是有台阶的**：树解析失败 → 重试 → 视觉；定位失败 → 重解析 → 视觉；视觉未配 → 明确报错 + 截图路径。不会"静默点错"。
4. **失败可解释**：返回里带候选文案、匹配数、最后界面摘要，模型能自己纠正一次，而不是盲目重试。

换句话说：**快是因为去掉了不必要的步骤，不是因为放宽了判定**。

## 5. 逐条对应你给的要求

| 你的要求 | 机制 | 为什么成立 |
|---|---|---|
| 1 插件入口/注册/结构，不改核心 | `package.json` 的 `dsh.bundle.patch` → `cordis.patch.yml` 的 insert；入口导出 `name/inject/Config/apply` | 只用 Cordis 公开扩展点（`ctx.tools`/`ctx.effect`/可选 `systemPrompt`），没有一行进 dsh 源码 |
| 2 轻量界面获取 + 缓存复用 | `uiautomator dump` → 结构化节点树；L1/L2/L3 分级 | 把"识别"换成"解析"；同屏读取不再付往返 |
| 3 高频动作封装 | `adb_tap/swipe/input/key/wait` 等 10 个工具 | 模型只填参数，坐标本地算，跳过"生成代码" |
| 4 失效兜底与明确触发条件 | 缓存未命中/动作后/探测不符→重解析；解析失败/定位失败→视觉 | 每一级都有写死的触发条件（README §5 表） |
| 5 合并批量指令 | `adb_batch` 先离线解析再一次性下发；按预算切段 | 往返从 N 次降到 1–2 次，且有超时保护 |
| 6 计时对比方法 | `timing.jsonl` + `adb_timing` + `bench.mjs` 实测量 | 口径可复现：`adbCalls` 与 `wallMs` 逐条记录 |
| 额外：命名核实 | npm/GitHub/本地三处查证 `dsh-quick-adb` 未占用 | 查证过程见提交说明；名称已统一到包名/插件 id/工具前缀/文档 |

## 6. 什么时候这个目标是达不成的（边界）

诚实地列出反例，避免过度承诺：

1. **界面没有结构**：WebView 未开无障碍、Flutter、游戏、DRM。此时杠杆一失效，速度回到"截图 + 识图"，插件只是把兜底做得更顺。
2. **任务本身需要视觉判断**：验证码、图表读数、颜色/布局审美判断。控件树里没有这些信息。
3. **强动画界面**：`uiautomator dump` 拿不到 idle 会超时，重试也慢。表现为单步退化到 1–2s。
4. **需要精确中文输入**：`input text` 不支持，必须装 ADBKeyboard；否则只能"输入成功但内容不对"——插件会告警，不会假装成功。
5. **网络 adb 且 RTT 很高**（>200ms）：合并往返的收益仍在，但单步下限被 RTT 抬高。

这些不是实现缺陷，而是方案的信息边界。插件选择"明确报错/告警"而不是"看起来成功"。

---

## 6.1 实测反例：固定坐标流水线

2026-11-01 的独立复测给出一个必须承认的反例：10 个动作的录制流水线，裸 adb 3729ms，插件 4911ms（+32%）。

原因完全符合上面的公式：这条流程 **H（命中）与 M（未命中）都不发生**，感知项为 0；剩下的只有 `N × (RTT + 封装开销 + 进程启动)`。插件每步多一层 Node 封装、各自拉起一个 adb 进程，于是比裸脚本更慢。

所以本方案的收益条件写清楚是：**每一步的决策依赖上一步看到的界面**。没有这个依赖，正确做法是用 `adb_shell` 拼一条命令或 `adb_batch` 合并，而不是逐步调工具。

---

## 7. 结论

能达成目标，不是因为写了更快的代码，而是因为**把模型从"每一步的执行者"改成了"每次决策的指挥者"**：

- 感知：位图 → 结构（去掉推理等待）
- 决策：生成代码 → 填参数（去掉生成与不确定性）
- 执行：多次往返 → 一次脚本（去掉线性 RTT）
- 复用：同屏重复读取 → 缓存（把 O(n) 变 O(1)）

四项各自独立成立，叠加起来就是 5× 的结构性收益；任意一项单独失效（比如换成自绘界面），其余三项仍然有效——这正是它比"换更快的模型"更可靠的原因。
